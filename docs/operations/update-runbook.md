# RelayDock 更新与发布运维手册

更新时间：2026-08-02

适用版本：`v0.6.6` 及后续稳定产品发布。

本手册面向 RelayDock 控制面管理员与发布维护者，补充根目录
[README](../../README.md) 中的简短操作说明。它记录更新路径、前置检查、
外置前端迁移、回滚边界和发布验收要求。

> [!IMPORTANT]
> 更新前始终从面板下载一份加密备份。二进制备份、网页软链接或安装器临时快照
> 都不能替代可恢复的数据备份。一次发布只运行一种更新路径；不要同时点击面板
> 更新、执行 `install.sh update` 或手工覆盖线上文件。

## 1. 更新路径与边界

RelayDock 有三种更新方式。它们的安全边界不同，不能互相替代。

| 部署状态 | 应使用的路径 | 更新范围 | 不适用场景 |
| --- | --- | --- |
| Linux 裸机 / systemd，面板可访问，目标是完整稳定产品发布 | 面板完整更新 | 控制端、内嵌或受管外置网页、守卫、Agent 安装资产、测速资产 | Docker、Windows、未受管外置前端 |
| 旧版、未完成产品发布迁移，或面板不可访问 | 命令行兼容更新 | 控制端、守卫、Agent 安装资产、测速资产；内嵌网页随控制端二进制更新 | 任意外置网页的自动切换 |
| Docker Compose | 宿主机拉取并重建镜像 | 容器镜像与挂载数据 | 容器内面板更新、裸机安装脚本 |

### 1.1 面板完整更新

面板从 GitHub 的最新正式 Release 读取产品清单。稳定产品包必须包含：

- `relaydock-release-manifest.json`
- `checksums.txt`
- 当前平台的控制端程序
- 网页归档 `relaydock-web.tar.gz`
- Linux AMD64 / ARM64 到期守卫
- Linux AMD64 / ARM64 Agent 安装资产
- Linux 与 Windows 的测速资产

清单把这些文件绑定到同一个 `release_id`、后端版本和 API 协议。面板不会把
未经清单验证的前端静态目录当作可安全覆盖的发布内容。

### 1.2 命令行兼容更新

安装脚本从最新 GitHub Release 下载控制端和本地安装资产，并验证
`checksums.txt`。它适合将旧版带到可使用面板产品更新的版本，或在面板损坏、
无法登录时恢复控制面。

它不是完整产品发布事务：不会读取产品清单、不会验证 API 协议或网页元数据，
也不会替换外置前端。因此，命令行成功后仍应检查外置网页的版本；后续稳定更新
应优先改回面板路径。

### 1.3 Docker Compose

面板会明确禁用 Docker 容器内原地更新。容器文件在重建后不可作为持久更新目标，
所以只能在保存 `docker-compose.yml` 的宿主机目录更新镜像：

```bash
docker compose pull
docker compose up -d
docker compose ps
docker compose logs --tail=100 arcway
```

`./data` 等数据卷不应删除。回退时将 Compose 中的镜像标签改为上一个已验证版本，
再执行 `docker compose pull && docker compose up -d`；如版本包含数据库迁移，
同时恢复更新前的数据备份。

## 2. 所有更新前的检查

1. 在面板下载并妥善保存加密备份，确认可以解密和下载。
2. 阅读目标 Release Notes，确认版本号、数据库迁移、兼容性和已知限制。
3. 确认没有另一项更新事务正在运行。面板出现“更新中”“恢复中”或“上次未完成”时，
   不要再次点击更新。
4. 确认控制端能访问 GitHub API 和 Release 资产，且本机有足够的临时磁盘空间。
5. 记录当前版本、部署方式和服务状态：

   ```bash
   systemctl status arcway --no-pager
   journalctl -u arcway -n 100 --no-pager
   ```

6. 对外置前端，确认它是否已经是受管目录。只要不是下文的 `current` /
   `previous` 结构，面板就不应尝试完整更新。

生产网页可读取以下元数据来核对当前公开版本：

```text
https://<panel-domain>/relaydock-release.json
```

该文件应与已安装发布状态、控制端提交和 API 协议一致。

## 3. 面板完整更新流程

### 3.1 适用条件

面板完整更新需要同时满足以下条件：

- Linux 裸机 / systemd 控制面；Docker 和 Windows 会被界面禁用。
- Release 是带产品清单的正式稳定发布。
- 当前控制面可以读取有效的安装状态和更新状态目录。
- 没有其他安装器或产品更新事务持有更新锁。
- 内嵌前端，或已迁移为受管目录的外置前端。

如果面板将“立即更新”禁用并提示原因，应按提示修复部署状态或改用命令行兼容更新；
不要跳过提示手工替换某一个文件。

### 3.2 管理员操作

1. 以管理员身份进入 **系统设置 → 系统更新**。
2. 点击 **检查更新**，阅读目标发布、组件列表、更新范围和 Release Notes。
3. 确认目标版本与当前版本符合预期后，点击 **立即更新**。
4. 保持页面打开直到进度进入“正在等待服务恢复”或“更新完成”。服务切换时浏览器
   连接会短暂中断；恢复后重新加载页面并再次点击 **检查更新**。
5. 检查组件状态全部为当前版本，确认公开 `relaydock-release.json` 与面板状态一致。

### 3.3 事务内部顺序

面板更新按以下顺序进行，因此“下载完成”不等于“已经切换”：

1. 从 GitHub 读取最新 Release、产品清单、Release 资产摘要和大小。
2. 校验 Release ID、版本、组件归属、SHA-256、二进制架构和 API 协议。
3. 将所有必需资产下载到私有暂存区；任一文件不满足校验时不修改线上文件。
4. 写入持久化事务记录并取得更新锁，避免并发更新或进程重启造成交错替换。
5. 由独立 systemd helper 停止控制面，备份数据库、控制端和本地安装资产。
6. 原子激活控制端、资产和受管网页发布目录；网页使用不可变版本目录与软链接切换。
7. 启动控制面并检查服务状态、内部健康接口、网页元数据和 API 协议。
8. 全部检查通过后写入已安装发布状态；否则恢复旧文件、数据库快照和网页链接。

更新 helper 独立于 `arcway.service` 进程组运行，避免正在被替换的控制面本身负责
停止、重启或回滚。主机在事务中重启时，未完成的事务仍会被恢复逻辑接管；面板会
持续拒绝新更新，直到其进入成功、失败或已回滚的终态。

### 3.4 前端的两种情形

| 网页来源 | 面板更新行为 |
| --- | --- |
| 内嵌前端 | 网页包含在控制端二进制中，随控制端一起更新。 |
| 受管外置前端 | 网页归档解压至新版本目录，然后原子切换 `current` 与 `previous`。 |
| 普通外置静态目录 | 面板拒绝完整更新，绝不擅自覆盖该目录。 |

## 4. 命令行兼容更新

### 4.1 何时使用

以下情形优先使用命令行：

- 控制面仍是旧版，尚未具备可靠的产品发布事务。
- 管理员无法访问或登录面板。
- 面板提示当前部署无法安全原地更新，需要先完成兼容迁移。
- 由一键安装脚本维护的 Debian / Ubuntu systemd 实例需要修复控制端或本地安装资产。

不要把“旧版先命令行更新”理解为绝对的功能限制。它是一条风险更低的迁移路径；
完成后是否可以使用面板，仍取决于版本、部署方式和外置前端是否受管。

### 4.2 执行命令

```bash
curl -fsSL https://raw.githubusercontent.com/violetaini/relaydock/main/install.sh | sudo bash -s -- update
```

脚本会识别现有 systemd 配置中的可用路径，保留当前端口和数据目录。它先下载并
校验资产，之后才停止服务；更新过程中会对控制端、守卫、Agent 安装资产、测速资产、
systemd 配置和数据库状态建立事务快照。新服务不能启动时，脚本尝试恢复这些内容。

更新结束后立即检查：

```bash
systemctl status arcway --no-pager
journalctl -u arcway -n 100 --no-pager
```

### 4.3 重要限制

- 不要在脚本运行时打开面板更新，也不要同时启动第二份安装脚本。
- 脚本更新内嵌网页所在的控制端二进制，但**不会**替换任何外置前端目录。
- 脚本不执行产品清单、API 协议、网页 `relaydock-release.json` 或公网网页健康检查。
- 外置前端如果仍是普通目录，完成命令行更新后仍需按下一节迁移，不能假定网页已更新。
- 跨越数据库迁移后再降级时，必须同时恢复更新前的数据备份；不能只恢复旧二进制。

## 5. 受管外置前端迁移与维护

### 5.1 目录约定

外置前端只有采用下列不可变版本结构，才能加入面板完整更新和自动回滚：

```text
<web-root>/
├── releases/<release-id>/
├── previous -> releases/<previous-release-id>
└── current  -> releases/<release-id>
```

`ARCWAY_WEB_ROOT` 必须指向 `current` 软链接，而不是任意可写静态目录。建议额外
配置 `ARCWAY_UPDATE_WEB_HEALTH_URL`，让产品更新在切换后验证反向代理实际公开的：

```text
https://<panel-domain>/relaydock-release.json
```

首次从普通目录迁移时，应先使用手动发布脚本生成受管版本并确认网页正常。面板会把
未受管目录标记为“待迁移”，而不是擅自认定它是最新版本。

### 5.2 手动发布与回滚

在后端仓库执行以下命令，替换连接参数：

```bash
./scripts/deploy-frontend.sh --host CONTROL_PLANE --port 22
```

脚本构建并校验完整网页版本，上传到新的不可变目录后原子切换 `current`。回滚到
上一个受管网页版本：

```bash
./scripts/deploy-frontend.sh rollback --host CONTROL_PLANE --port 22
```

手动网页发布只适用于维护和迁移；正式产品 Release 发布后，应优先由面板完整更新
统一处理控制端与受管网页。不要用 `cp`、`rsync --delete` 或直接覆盖 `current`
所指向的目录来替代版本切换。

## 6. 故障处理与回滚原则

### 6.1 面板更新失败

1. 不要重复点击 **立即更新**；先让现有事务完成成功、失败或回滚。
2. 在面板查看事务状态和错误提示，记录目标 Release 与失败阶段。
3. 在宿主机检查服务和日志：

   ```bash
   systemctl status arcway --no-pager
   journalctl -u arcway -n 200 --no-pager
   ```

4. 确认公网 `/relaydock-release.json` 是否仍对应旧版本或已成功恢复。
5. 只有在事务已经结束且原因已修复后，才重新执行 **检查更新**。

面板事务会在健康检查、网页元数据或 API 协议不满足条件时自动恢复旧控制端、资产、
数据库快照和受管网页软链接。若日志显示恢复本身失败，停止进一步修改并先从加密备份
恢复到已知版本，再排查磁盘、权限、systemd 或网络问题。

### 6.2 命令行更新失败

安装脚本会尝试恢复事务快照，并在无法完全恢复时保留临时备份路径。此时应：

1. 保存脚本输出和 `journalctl -u arcway -n 200 --no-pager`。
2. 不要删除脚本提示保留的事务备份。
3. 确认原服务是否已恢复为 active；若未恢复，按备份和日志进行人工恢复。
4. 处理根因后再选择命令行或面板路径重新尝试，避免反复混用两种更新器。

### 6.3 数据库与降级

任何可能包含数据库迁移的发布，都必须把“应用二进制回退”和“恢复相同时间点的
数据备份”视为一个操作。仅替换旧 `arcway` 程序可能导致新旧 schema 不兼容。

## 7. 发布维护者清单

稳定 Release 不能被视为只有后端或只有前端的发布。发布前至少确认：

1. Git 标签、后端版本、产品清单 `release_id` 和 API 协议一致。
2. 前端产物已进入 `internal/web/dist/`，并生成带版本信息的网页归档。
3. Release 含完整控制端、守卫、Agent 安装资产、测速资产、网页归档、清单和
   `checksums.txt`。
4. 清单中的资产大小、SHA-256 与 GitHub Release 资产摘要一致。
5. 前端类型检查、单元测试和生产构建通过；后端 `go test ./...`、`go vet ./...`
   和构建通过。
6. 通过 `scripts/release-bundle-contract_test.sh` 和
   `scripts/release_transaction_test.sh`，覆盖发布契约、成功切换和健康检查失败回滚。
7. 发布后在控制面与所有受管服务器检查服务、心跳、流量、实时状态和网页元数据。

同名 Git 标签不可重打。若发布被取消、资产不完整或契约校验失败，应修复后使用新的
版本号重新发布。每次稳定发布和生产验收后，更新
[项目状态与发布进展](../project-status.md)。

## 8. 验收记录与责任边界

`v0.6.6` 已完成产品包、事务成功/回滚演练、CI 以及生产控制面和受管节点验收。
详细证据、版本提交和下一次真实面板发布的验证边界记录在
[项目状态与发布进展](../project-status.md)。

本手册描述的是可重复的运行规则，不应替代目标 Release Notes 或实际面板显示的
兼容性提示。面板的更新范围、组件状态和拒绝原因是当前实例是否能够安全更新的
最终依据。
